# Web 互动项目 Agent 开发指南

适用于 `PhotoGallery/docs/<project-id>/` 下的网页项目，以及未来读取项目登记表的独立门户。Android 原生应用请使用仓库现有 Android 专项指南。

开始任务前先阅读：
1. [项目管理规范](./PROJECT_MANAGEMENT_STANDARD.md)
2. [项目登记表](../projects.json)
3. 目标项目的 `README.md`（如存在）
4. 目标项目现有测试、CI 和源码

## 1. 接单与范围确认

开始写代码前明确：
- 项目 ID 和固定访问 URL。
- 本次目标、非目标和必须保留的行为。
- 涉及文件、资源和外部依赖。
- 验收标准，以及哪些验证需要真实浏览器或真实 GPU。

若任务没有明确项目 ID，先从路径、登记表和上下文确定；不能确定时只问一个必要问题。

## 2. 建立基线

修改前：
1. 确认分支、HEAD SHA 和工作区状态。
2. 阅读目标项目入口与相关模块，不从截图或旧总结猜测代码结构。
3. 记录固定 URL、主要交互和已知问题。
4. 视觉/动画问题保存修改前截图；数值/物理问题保存可复现输入输出。
5. 识别现有测试和 CI，不重复造轮子。

没有基线时，不得声称修改前后已经量化对比。

## 3. 先定义验收，再实施 TDD

- 可单测逻辑：先写复现问题的失败测试（Red），再最小实现（Green），最后整理（Refactor）。
- UI/视觉问题：固定视口、场景、相机和操作步骤，再建立浏览器检查或截图证据。
- 仿真/GPGPU：优先测试不变量、边界条件、粒子数量切换、初始化失败和资源释放。
- 纯内容/布局调整可轻量验证，不为形式增加复杂测试框架。
- 每轮只处理一个清晰切片，避免同时改相机、布局、物理模型和 UI。

## 4. 实施约束

- 尽量只修改目标项目目录和必要的登记/说明文件。
- 保持 `id`、目录名、`index.html` 入口和既有 URL 稳定。
- 不修改其他项目，不做无关格式化，不替换用户确认过的设计基线。
- 资源路径使用项目相对路径；检查 `/PhotoGallery/<id>/` 子路径部署。
- 外部依赖固定版本；新增依赖说明理由。
- 不把密钥写入静态页面。
- 如需跨项目改动，先说明影响范围并增加回归检查。

## 5. 必须执行的验证

按复杂度选择，报告必须列出实际结果。

### 所有项目
- HTML/JavaScript 语法检查。
- 本地资源和引用路径检查。
- 固定入口与关键 DOM/初始化路径检查。
- `node scripts/validate-project-catalog.mjs`。

### 有交互的项目
- 在真实浏览器打开固定入口。
- 完成至少一条主要用户操作路径。
- 检查刷新、重新进入和窗口缩放。
- 检查桌面和窄屏视口的关键布局。

### L2/L3 项目
- 运行项目已有逻辑测试。
- 运行 Playwright 或等效浏览器回归。
- 视觉项目检查截图，不只看测试退出码。
- 仿真项目检查数值不变量、边界条件和性能测量方法。
- WebGL/GPGPU 项目记录浏览器、GPU/驱动或 CI 渲染后端；CI 软件渲染通过不等于真实 GPU 验收。

**严禁把未执行的测试写成通过。** 如果当前 Agent 环境不能运行浏览器/WebGL，必须标记「未验证」并给出用户可执行的验证步骤。

## 6. 更新项目登记表

以下情况必须同步更新 `docs/projects.json`：
- 新增或删除项目。
- 名称、简介、分类、标签或技术栈变化。
- 主入口、源码仓库或下载地址变化。
- 状态在 idea/development/testing/published/archived 之间变化。

普通 bug 修复不需要修改目录元数据。若更新 `updatedAt`，必须按实际日期填写。

本阶段星海页面仍有一份内嵌项目展示数组。修改其中的展示元数据时，必须同时核对登记表，不要只更新一份。

## 7. 发布前检查

1. 检查 diff 和改动文件清单。
2. 运行目标项目测试。
3. 运行项目目录登记校验。
4. 检查其他项目入口没有被误改。
5. 检查相对路径、大小写和固定 URL。
6. 检查控制台错误和明显性能退化。
7. 确认是否需要更新 README、build marker 或版本说明。

## 8. 提交规范

使用：

```text
feat(<project-id>): ...
fix(<project-id>): ...
perf(<project-id>): ...
test(<project-id>): ...
docs(<project-id>): ...
chore(portal): ...
```

提交说明必须包含修改目标、关键实现、实际测试结果、未执行的验证、剩余风险，以及对固定 URL/其他项目的影响。

## 9. 交付报告模板

```text
项目：
目标：
根因/需求：
修改文件：
实现摘要：
测试执行：
- [通过/失败/未执行] ...
浏览器验收：
- 浏览器/视口/场景：
- 实际结果：
部署：
- Commit：
- Pages 状态：
- 固定 URL：
未解决问题/风险：
```

部署成功、文件已推送、浏览器实际显示正确是三个不同状态，必须分别报告。

## 10. 可直接交给 Agent 的提示词

```text
请先阅读 docs/web-projects/PROJECT_MANAGEMENT_STANDARD.md、
docs/web-projects/AGENT_DEVELOPMENT_GUIDE.md 和 docs/projects.json。

本次只处理项目：<project-id>
目标：<具体目标>
必须保留：现有项目 ID、docs/<project-id>/index.html、固定 URL 和已确认交互。
先检查代码与测试，记录基线，写明验收准则，再按 Red → Green → Refactor 实施。
不要修改其他项目或 Android 应用。
完成后运行项目测试、目录校验和真实浏览器验收；无法执行的项目必须明确标记未验证。
如展示元数据或入口变化，同步更新 docs/projects.json。
最后报告修改文件、根因、测试证据、部署状态和 Commit。
```
